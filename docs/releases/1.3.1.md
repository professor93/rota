## rota 1.3.1

### Changed for people coming from 1.3.0

- **A home whose daemon has given up on its login is refreshed.** Claude Code's daemon refreshes the login itself, and now and then the refresh fails, on a plain `~/.claude` as much as in a home of rota's. When the access token had run out by then, the sessions the daemon hosts said `Login expired · Please run /login`. The daemon goes on retrying without logging a failure, while rota, seeing something alive in the home, waited for it to go away, and an account could sit like that for days on a login that was alive. Now every look, a listing of any kind, maintenance or a launch, refreshes such a home whatever else runs there, writes the login into the store, and says so in one line. rota expects Claude Code to read it from the store, as its code path suggests it does; no live daemon has been observed recovering this way yet.
- **A store Claude Code blanked no longer makes an account dead by itself.** Claude Code empties the login in its store when a refresh of its own comes back refused, and that has been measured not to be final. An account whose current login was blanked now presents its own refresh token once first, whether the home is alive or quiet. On success the login goes back in; on a refusal the account is dead and says why, and that token is never presented again; on a failure that says nothing about the login the account stays alive, says so, and the next look tries again.
- **A failed write after a refresh is an error, and the next look finishes it.** Once the provider has answered, the login in the home is spent, so a home that cannot be read or written names the account and says so. What is owed is saved with the token, so the write needs no other refresh.
- **`rota list` says when a login ends.** In its last three days the STATUS column reads `ok (login ends in 2d)`, and `ok (login ended 3h ago)` once it is over, because sessions that outlive a login stop making progress and cannot recover by themselves. The line under the table in the last five days stays, for `--short`, and says what to do.
- **A dead account always says why.** A login Claude Code cleared and the provider then refused reads `Claude Code cleared the login in its home, and the provider refused rota's own refresh token too (...)`, and an account marked dead by a rota that kept no reason says that much instead of nothing, in `rota list`, `--json` and `GET /v1/accounts`.
- **A CLI is asked to stop before it is killed.** On Linux and macOS a cancelled run, a timeout or a run over a bound sends SIGTERM to the CLI's process group and SIGKILL three seconds later to whatever has not gone. Claude Code rotates its refresh token, and a process killed between the provider accepting a refresh and the store saving it loses the login for everything in its home. A CLI that stops when asked costs nothing, and a run returns as soon as its process group has gone; one that does not stop holds its run for those three seconds. A run rota stopped is an error with exit code -1 whatever its CLI exits with, as it was when such a CLI was killed. Windows is unchanged.
- **More inherited variables are dropped.** `CLAUDE_CODE_SIMPLE`, `ANTHROPIC_PROFILE`, `CLAUDE_CODE_USE_FOUNDRY`, `CLAUDE_CODE_USE_MANTLE`, `CLAUDE_CODE_USE_ANTHROPIC_AWS`, `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`, `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID` and `CLAUDECODE` no longer reach a claude account's CLI, on any route: each would change how it signs in, stop it reading its login at all, or tell it that it runs inside Claude Code.
- **On macOS a credential file newer than the keychain item is the login.** Claude Code keeps the login in the file when the keychain refuses a write, so the file is not always the stale copy. rota reads the newer of the two; in a quiet home a file no newer than the item is removed as before, and a newer one stays and the older item goes instead, so Claude Code reads it too. A blanked item counts as older than any file that holds a login, and goes even with something alive, once what it kept beside the login is in the file. A blanked file never wins.

### What to do

Nothing. rota refreshes an account stuck on `Login expired` the next time it looks at it. A login the provider really did refuse goes dead and says so, and an account a rota before this one already marked dead stays dead: `rota login`, or `/login` inside one of its windows.

### A stranded home

- It takes all of this: rota keeps the login in that home, the account is alive and out of the hold, the home holds the account's own current login, the store's lock is held, something is alive there, `daemon-auth-status.json` says `auth_required` about the token that ran out, and that token truly expired at least ten minutes ago. Where Claude Code does not write that file, on its storage-v5 path say, a home is not found stranded.
- The status file outlives recovery, so on its own it means nothing: with a good token rota does nothing, and a file older than the token that ran out is about some earlier token.
- A window open beside the daemon, or a run holding the account, stops nothing: it has had its chance by then. A home whose token is not that far gone, or that no daemon has reported on, stays its own, as does everything else about the rule that rota leaves a live home alone.
- A listing rescues whatever it is asked to show: `--short` and a reading under five minutes old do not put it off.
- While it refreshes and writes, rota holds Claude Code's own refresh lock, `.oauth_refresh.lock` in the home, for one account at a time, and touches it every five seconds as Claude Code's own holders do. A lock somebody holds leaves this look to them, a lock somebody took meanwhile is neither touched nor removed, and the home is read again once rota has it.
- A refusal goes as any refusal does: the home is read again first, a sibling's login is taken, and otherwise the account is dead and its token never presented again. A refresh that does not get through changes nothing, and a launch joins the home as it always did.
- A store whose lock was released rotates nothing, here as everywhere.

### For the SDK

- `Account.WhyDead` is why an account needs a login, in words for a person, and `Account.StagedCurrent` whether its home holds its current login. `wire.LoginStatus` is what the STATUS column says about a login's end.
- `Store.Rescue` does what a home is owed and reads no usage, for a listing that reads none. `Store.Refresh` and `Store.Maintain` do the same first.
- `Run` and `Start` stop a CLI as above when their context is cancelled, and return once it has gone, at most three seconds later than they used to. The result of a run rota stopped keeps `IsError` true and `ExitCode` -1 whatever the CLI exits with.
