## rota 1.4.0

### New in 1.4.0

- **A claude account on a Claude Console API key.** `rota login --key` reads the key with the terminal's echo off, or as one line of standard input when that is not a terminal, and makes an account of its own, billed per token to that key's Console credit. `--label` names it; otherwise it is `api key ...` and the key's last four characters, which are the only part of it anything ever shows. Over HTTP, `POST /v1/login` takes `{"key":"...","label":"..."}` and answers at once.
- **A token from `claude setup-token`, pasted.** `rota login <id> --token` reads it the same way and stores it as that account's long-lived token, the field `rota login --long` fills, good for a year counted from now. Over HTTP it is `{"account":1,"token":"..."}`. It never makes an account, and an account on a key takes none.
- **Never from the command line.** Neither credential is ever taken from an argument, where every process and the shell's history could read it. A key typed where an argument goes, `rota login sk-ant-…` above all, is refused without being repeated, by every command: as an unknown command, flag, account id, flag value, run id, prompt, the first `--input` message, or a directory for `rota set` or `PATCH /v1/accounts`. The error a command ends with, in text or JSON, and each error `rota serve` prints, has anything shaped like an Anthropic credential taken out.

### New in the next beta

- **A refresh lock Claude Code takes over from a stalled rota is no longer counted as rota's.** rota touches the lock it holds every five seconds; a touch that came at the moment Claude Code, having judged the lock dead, made its own in its place could touch Claude Code's lock, count it as rota's, and remove it when rota let go, leaving Claude Code's refresh unguarded. Now no beat counts another lock as rota's, so letting go leaves it in place. On Linux and macOS rota keeps the directory it made open while it holds the lock and touches only that one, so such a lock is never touched; on Windows a beat at that very moment can still touch it once. Letting go looks at the lock just before removing it, which leaves only that instant.

### New in 1.4.0-beta.10

- **A Claude login's 30-day end is known, and nothing is presented past it.** rota learns the end from `rota login`, from every refresh it makes and from the account's home. Once it has passed, rota presents the refresh token to no one, by any look: the account goes to `re-auth needed (its login ended on … UTC: a Claude login lasts 30 days from sign-in; rota login <id> makes a new one)`, whatever else a look would have said. `rota list` warns in the last 72 hours: `login ends in 47h (2026-11-10); rota login 13 before then`. For the SDK, `Account.LoginEnded()` is new, `Account.LoginUntil()` now gives the end in effect and has a value from `rota login` on, and `wire.LoginSoon` is 72 hours instead of 5 days.
- **Every refresh of a Claude login kept in a home holds Claude Code's refresh lock.** A launch, `rota list`, `rota serve`'s maintenance and a run on a token now take Claude Code's own refresh lock, as the rescues already did, and read the home again once they hold it. A Claude Code that starts mid-refresh waits for rota's new login instead of presenting the same token; a rotation Claude Code has just finished is taken instead of spent again; a refresh whose answer never came is not presented again before that read; and a lock Claude Code holds leaves the refresh to it: a look goes on with no error, and a run that needs a fresh token in its environment is told to try again in a moment.
- **A Claude account no longer gets stuck on an old login after one odd look at its home.** Before, once a look found the home empty, blanked, unreadable or behind, or the macOS keychain briefly answered "no such item", rota stopped following Claude Code's refreshes, later presented a token that had already been replaced, and the provider revoked the login. Now each later refresh is picked up, one of a grant the provider has shortened included. Where the home's login was last found in its keychain item, a missing item is asked for twice before rota acts on it, and while anything runs in the home such a read changes nothing rota believes, unless rota itself holds Claude Code's refresh lock, when nothing can be rewriting the item and one that is missing is missing.
- **A blanked or stranded login is rescued only with a copy rota saw a moment ago.** rota presents its own copy only when one of its looks saw the home holding exactly that token at most ten minutes (two watcher intervals) before the blank was first found. Otherwise it presents nothing and marks the account dead: `Claude Code's refresh was refused and rota's copy is older than the home's last look, so rota did not present it; rota login <id> makes a new login`. Before, rota presented a token Claude Code may already have spent, which revokes the whole login. On macOS a stale credentials file beside a blanked keychain item is no longer taken for the login or put back in front of Claude Code, and rota's own seed file there is removed once Claude Code has moved the login into the keychain. A daemon makes the look these rescues are judged by for the claude accounts of the sessions it holds, as it starts and every five minutes after, whatever `refresh_every` says.
- **Refreshes leave a journal, and a refusal is no longer masked.** rota keeps `refresh.log` beside the store, with a line for every refresh its store makes, for any provider, and for every change a look finds in a claude home: JSON Lines, mode 0600, moved aside at 1 MiB, token fingerprints only. A refresh rota does not make says why, such as `skipped:login-ended`, `skipped:lock-held`, `skipped:older-copy` or `skipped:caller-left`. A refusal the home's login then covered is no longer silent: rota warns that it presented a token the provider had already replaced and keeps `last_refusal` on the account, and a later "Claude Code cleared the login" death ends with `(rota had presented a replaced token at HH:MM UTC)`. For the SDK, `store.WithCaller(ctx, name)` names who refreshed, for the journal.
- **A refresh rota has sent is no longer lost when whoever asked goes away.** A client hanging up on `?refresh=1`, a run or a WebSocket start, `rota serve` stopping, or an interrupt or closed terminal during `rota list` or any form of `rota run`: the refresh goes on to the provider's answer, the save and the write into the home, for up to 35 seconds. Nothing is sent after that, and the command exits with status 130 without starting a CLI, still reporting anything that went wrong beside the interrupt; an interrupt once the CLI is running behaves as before. `rota serve` and the daemon of `rota serve start` stop their background sweeps as soon as their shutdown begins, and before exiting wait up to 45 seconds for every refresh still under way, saying so in their log. A holder preparing a held session finishes a refresh under way on SIGTERM or SIGHUP in the same way, and starts no CLI. For the SDK, `store.RefreshTimeout`, `store.Settle(ctx)` and `store.Left(err)` are new, and `Store.Preparing` is a hook that `Run`, `Start`, `Prepare` and `PrepareIn` make a launch inside, heeding its context beside the caller's.

### New in 1.4.0-beta.9

- **Held sessions, which outlive the daemon.** `rota serve start` runs a daemon for the store, and each terminal it starts runs in a process of its own, `rota serve hold`, which keeps the CLI on a pseudo-terminal with its screen and its scrollback and lives exactly as long as the CLI. Stopping, restarting, upgrading or crashing the daemon ends no session: the next daemon takes up every one still running, and a viewer's offsets go on meaning the same bytes. A holder that goes without recording how its CLI ended, as when it is killed or the machine reboots, leaves its session `interrupted` with its conversation kept, and nothing restarts by itself. The holder prepares the account itself, so no token passes between processes, and the account stays claimed for as long as the CLI runs (a codex session's, while its holder lives) and no longer: a held codex session's account is free once it ends, as an interactive one's is, even while Codex's daemon keeps running. Linux and macOS.
- **`rota serve start | stop | status | install | uninstall`.** One daemon for each store. `start` runs it in the background, with nothing of the terminal it was typed at or of the account a CLI rota launched runs as, and says its pid and control socket; when one already runs it names it and exits 0, and two at once make one. `stop` leaves every session running for the next daemon, and `stop --all` ends them too, asking first. `status` says whether one runs and how many sessions it holds, exits 0 with a daemon and 3 without, and takes `--json`. `install` makes it a systemd user unit or a launchd agent that starts at login, and `uninstall` takes it away; neither supervisor stops a session when it stops or restarts the daemon. It opens a TCP port only where `server.toml` sets `[server] listen` and `--ctl-only` is not given, and logs to `<store>/daemon.log` or to `[server] log_file`. In what the five print, a control character in a path, an address, a version, a session's id, a failed start's log lines or a supervisor's answer is drawn as a space, and `--json` keeps every value as it is.
- **`rota run --detach`** hands the account's CLI to a held session instead of to this terminal and returns, starting it in this folder, at this terminal's size and from this command's environment, less the variables that describe another terminal and the marks of a Claude Code or Codex session it was typed in. The CLI's arguments go after `--`; a prompt, `-p` or `--share` is a usage error. `--label` names the session. With no daemon running, it starts one on its control socket alone. An account a held session is running is busy as under any run (a codex account; a claude account's runs share it), and `rota run` on it names the session.
- **`rota send` into a held session.** `rota send <name> "text"` types the text into a held session named by its label, its name, its folder or its id, once its CLI is ready for a message, then Enter, waiting up to 30 seconds. A session waiting on a permission or a question is refused unless `--force`, and one whose keyboard somebody else holds is refused always. Success prints nothing. Over HTTP it is `POST /v1/terminals/{id}/messages`, as a run's is.
- **`rota list --sessions`** adds a `Held sessions` section, read from the sessions' records whether or not a daemon runs, and `--json` adds a `held` list, each session as `GET /v1/terminals` describes it, which is also what `rota run --detach --json` prints. A record that cannot be read is left out with a line that says so, and a held session's CLI is not listed again under `Running instances`. Both are there only when there are held sessions, so a store with none lists exactly what it did. On a terminal narrower than a row, a held session's row is fitted as the sessions' are, the name and the folder cut first and the start of its id never, and a name in Chinese, Japanese, Korean or emoji lines up by the columns it takes; a pipe or a file gets every cell whole.
- **The control socket.** The daemon serves its whole API, whatever `[routes]` says, on `<store>/terminals/ctl.sock` to this machine's own user, as the principal `local` and with no token: the socket's `0600` and the kernel's word on who connected are the whole authorization. A caller inside a held session, the agent in it or any command it runs, may only watch there.
- **`rota serve uninstall` that cannot reach the supervisor keeps every session.** With no user bus to reach, from `su`, `sudo -u` or a cron job say, `systemctl --user disable --now` fails and the daemon goes on running under the unit, and systemd, once it reloads a unit whose file is gone, no longer has its `KillMode=process`: the daemon stopping then ends every session in it. So uninstall first stops the daemon as `rota serve stop` does, while the unit is still loaded as it was written, and waits for its process to exit, which may finish serving for up to 10 seconds after it lets go of the store; only then does it delete the file and its `default.target.wants` link, asking for no reload. It exits 1, naming what systemctl said and what became of the daemon: stopped by uninstall, or no longer running when it went on its own, and that the file is kept when it could not be deleted. A daemon it cannot stop, or whose process has not exited within 12 seconds, keeps the file and the link where they are, and uninstall says the daemon is still running and to run `rota serve uninstall` again from a login that has a user bus. A launchd agent that will not boot out is handled the same way.
- **A caller inside a held session is refused on the control socket in its own words**: *this caller may only watch; nothing here can be changed from it*, since it signed in to nothing. A token, a page's user and an invite are told *this sign-in may only watch; nothing here can be changed from it*, as before.
- **The holder answers the CLI's terminal queries**, among them device attributes, its version, its colours and the cursor position, the same whoever is attached. A viewer's own terminal's answers are taken out of its typing, so the CLI is never answered twice.
- **The holder keeps a held session's screen up to 200,000 cells**, 500×400 say, for a viewer that attaches or falls behind. A larger session, or one whose screen is far behind a flood of output, is replayed to the viewer instead, and keystrokes, a stop and a send never wait for the screen.
- **`[terminal] keep_stopped`**, a week by default, is how long an ended or interrupted held session stays listed before its directory is deleted.
- **`[auth] local_user`** names the `[[users]]` entry the control socket's `local` types as on a held session when more than one may control, so `rota send` from this machine and that user on the page are one person at the keyboard.
- **The size.** The program's module now requires github.com/charmbracelet/x/vt, which keeps each held session's screen, and the charmbracelet packages it is used with, ultraviolet and x/ansi; the root module still requires nothing. The linux-amd64 binary is 11.5 MB, against 10.4 MB at 1.4.0-beta.2.

Foreground `rota serve` is unchanged: its terminals are in its own process, as before, and stopping it ends them; it takes no daemon lock and opens no control socket.

Not yet, and not everywhere: attaching to a held session from a terminal comes in a later beta, and until then it is watched and typed at on the terminal page, and `rota send` types into it. On Linux a held session is sure to outlive its person's logout only under `rota serve install` with lingering on, which `install` says how to turn on. On macOS launchd's default would hold the daemon and every session it holds at priority 20, so the agent sets `Interactive`. Watch-only on the control socket is a guard against accidents, not a wall. Windows has none of this: every held-session command refuses there.

### New in 1.4.0-beta.7

- **A codex login is left to the daemon Codex runs in its home.** An interactive codex session leaves Codex's app-server daemon running after it ends, and the daemon refreshes the login itself, at the same five minutes before expiry rota uses. While that daemon is alive, rota reads back what it wrote and refreshes nothing itself, for a run or in `rota serve`'s maintenance, so the daemon is never left presenting a refresh token rota had already spent, which codex refuses for good. Maintenance now saves a rotation it reads back. An `auth.json` that already holds the login rota would write is no longer written again, so what Codex adds to the file stays.
- **A codex token read back from its home is never presented twice.** `rota serve`'s maintenance refreshed a codex login in the store alone, and a token Codex had rotated in the home, once read back, was not recorded as the one the home held. So the next sweep took the file rota had refreshed past for a newer rotation, read the spent token back over the good one and presented it again, and codex refused it for good: the account went to `re-auth needed`. This could happen in every release up to 1.4.0-beta.5 when Codex itself had rotated the token in the account's home, most often through the daemon an interactive session leaves running, and the server's maintenance later refreshed that token itself, with no run of that account in between. A token read back is now recorded as the home's, and so is a file that holds the store's own token, whatever rota last recorded of its own write. Before it refreshes a codex login, the maintenance writes that login into the home and saves the store, and a sweep that cannot save refreshes nothing; a token it refreshes is saved at once and then goes into the home, as a run's does.
- **An account spent until its window resets is picked again once it has.** A usage reading taken before one of its windows resets is read again on the next look after the reset, five seconds after for the provider to roll it over, rather than when the five-minute cache runs out: a bare `rota run`, `rota list` and a bare run over HTTP see the account whole again and the rotation goes back to it. `rota serve` wakes its background sweep a few seconds after the soonest reset it knows of, one timer for the whole store, so the listing's `default` moves back without a request. A reading taken after the reset it reports waits for the cache as before. For the SDK, `store.ResetGrace` is the five seconds and `(*store.Store).NextReset` says when the soonest reset puts a reading out of date.
- **A key out of credit is passed by for an hour.** When Claude Code ends a run on a Console API key with `Credit balance is too low`, the rotation passes that account by for an hour, once the run is over. `rota list` says `out of credit (59m)` under STATUS; JSON says `"status":"limited"` with `no_credit_until`. It still runs by id, and a run on it the API answers, or the key pasted again with `rota login --key`, puts it back at once. A question, `--input` and runs over HTTP count; a terminal handed to the CLI does not.
- **A settings file that would send an account's login elsewhere is named at launch.** Claude Code applies the `env` block of a settings file over the environment rota gives it, so `ANTHROPIC_BASE_URL`, another credential, a proxy or `CLAUDE_CONFIG_DIR` there, or an `apiKeyHelper`, undoes what rota keeps out of a claude account's run. Every launch of a claude account, `rota run` with or without a prompt, a session, and `rota serve`'s runs and terminals, now reads the settings files that launch's Claude Code reads: yours, the project's and its local one, and the machine's managed settings. When one sets such a key it prints one warning naming each file and key, never a value; a proxy or certificates in your own or the machine's managed settings, which a corporate network sets on purpose, are said as what they are rather than as a login going elsewhere, while in a project's files they are named as the risk. A file is read as Claude Code reads it, a byte-order mark or UTF-16 included, up to the same 2 MiB. rota changes no file and stops no run, and a launch whose settings set none of these says nothing new.
- **Consent to an organisation's remote settings is the account's own.** Besides the policy and remote settings, an account's home now links neither `remote-settings-consent.json`, what the login agreed to of them, nor `remote-settings-helper-consent`, saved with them, nor `.session_ingress_token`, the token a self-hosted runner gives one session, nor any name that is one of them followed by a dot. Claude Code reads and writes that consent without following a link, so through rota's link it could keep none and asked again each time; and two accounts of one organisation no longer replace each other's. A link an older rota made for one of them goes on the first launch that finds the home quiet; your own files are left as they are.
- **An account's name, and an id or a path on one of rota's status lines, stay on one line.** A newline in an account's name is drawn as a space too, in the lines that name it, among them the line a run starts with, a login's and a sign-in's, `rota show`, `rota remove`, the notes under `rota list` and the watcher's warning. A tab, an escape or a newline is drawn as a space in the paths `rota show`, `rota remove` and a sign-in print, the session id a run ends with, the id `rota send` answers with, and the id and path a shared run opens with. `--json` keeps every value as it is.
- For the SDK, `rota/store` has a new method, `Store.PrepareIn(ctx, a, dir)`: `Prepare` for a CLI that starts in `dir` rather than in the calling process's directory, so the settings read for it are that directory's project's. `rota serve` terminals use it.
- For the SDK, a session whose CLI is gone before its prompt reaches it ends with that CLI's exit, which `Wait` reports as `Run` would, and a later `Send` names the failed write. `Start` used to return the broken pipe instead, but only when the CLI died just before the write rather than just after it.

### New in 1.4.0-beta.5

- **A name in Chinese, Japanese, Korean or emoji lines up.** Every width in the table is counted in the columns a character takes on screen, two for these, and an emoji spelled with several characters, a flag, a skin tone, a family or a ❤️, counts as the one picture a terminal draws. So the border after such a name sits where the frame's does, on a terminal and in a pipe or a file, where it used to be pushed right: a pipe or a file with such a name in it now gets its table lined up, and one without gets exactly what it got before. A wrap or a cut never halves a wide character or an emoji.
- **`rota list --sessions` fits the terminal it is on.** On a terminal narrower than a section, each running instance and each session stays one line, and what is free text is cut first: a title keeps its start and a directory its end, each kept eight columns wide until the account has been cut as far; then the account, at its end; and the session id last of all, since an id cut short resumes nothing. The lines under the sections wrap at their spaces, two spaces in. A title or a directory in Chinese, Japanese, Korean or emoji is measured by the columns it takes, in a cut and in the padding, so its row lines up on a terminal and in a pipe or a file alike, and a tab or another control character in one is drawn as a space. A pipe or a file gets everything else exactly as before.
- **A narrow `rota list` leaves short columns out instead of cutting them, and says which.** On a terminal narrower than the table, STATUS wraps to 24 columns and ACCOUNT to 16, and then CHECKED and UNTIL are left out whole; STATUS wraps on to 16, and only then is CLI left out, so a claude account and a codex one still read apart at 70 columns. `--short` leaves out CLI and then CHECKED. At 80 columns the readings keep their reset times and a dead account's reason takes four lines. Past that STATUS and ACCOUNT wrap on to 10, and USAGE is cut between the words of a reading as before. No header is cut any more, and neither are `#` and ID. A note under the table names every column left out: a wider terminal, or `rota list --json`, shows them. A pipe, a file and `--json` leave nothing out.
- **A tab or an escape in `rota list`, a warning, an error or an account's name is drawn as a space.** A control character, or a byte that is not UTF-8, in an address, a label, a reason, a provider's note or error, or a directory under `--sessions` is drawn as a space: in `rota list`'s tables and the notes under them, in every warning rota prints, the watcher's log included, in the error a command ends with, `rota serve`'s log file included, and in every line that names an account, which without a `--label` is the email its provider gave: the line a run starts with, a login's and a sign-in's among them. A newline in a line under `--sessions` is a space too, so it stays one line two spaces in. The tables stay lined up, and none of these can recolour, retitle or clear the terminal. `--json` keeps every value as it is.
- **`rota list` and the SDK's `Usage` ask nothing for a claude account rota holds no access token for**, as said under Changed for people coming from 1.3.2 and For the SDK.
- **A map's keys are written in sorted order, the same every time.** rota has written a map's keys in Go's random order since 1.0.0; now every JSON it writes, `--json`, HTTP and WebSocket replies, the SDK's Encode and the store files, puts a map's keys in sorted order. Store files get their keys reordered once, on the next save.
- **A Console API key where a setup token belongs is refused on the machine.** `rota login <id> --token` on standard input, or `POST /v1/login` with `"token"`, turns a Console API key away before anything is sent.
- For the SDK, the new `rota.PasteLong(provider, s)` reads a pasted setup token without a network call and refuses a Console API key.

### New in 1.4.0-beta.4

- **`rota list` fits the terminal it is on.** A terminal narrower than the table, one of 80 columns say, gets the long cells wrapped at their spaces inside their columns, STATUS first and then ACCOUNT, so every border stays where it belongs; an address too long for its column breaks before its "@". Only a terminal too narrow even for that has its other cells cut: USAGE first, between the words of a reading, so a spent window reads `5h 100%…` or `5h…` and never `5h 10…`; then the short columns; and STATUS and ACCOUNT last of all, below about 45 columns. Each cut line keeps its start and ends in one "…", and a wrapped column narrower than its name has its header cut the same way, to `ACC…` or `STA…`. The notes under the table wrap at their spaces too, and a command in backticks stays on one line unless it is wider than the terminal. A pipe, a file and `--json` get exactly what they got before.

### New in 1.4.0-beta.3

- **`rota serve` can log to a file and say nothing on the terminal.** `log_file` in `[server]`, or `--log-file PATH`, sends every line the server writes — the start-up line and its warnings, the requests it logs, the http server's own errors — to that file instead of stderr. `quiet` still decides how much, and the server's own plain lines are dated. A server that fails to start, or stops on its own, still says why on stderr. Like `quiet`, it is a key and a flag, with no environment variable. Empty, the default, is stderr exactly as before.
- **The file is the owner's alone and never a way in.** The path must be absolute and its directory must exist. Each time it is opened, at the start and after every rotation, a link there is never followed and a FIFO never waited on; the file is appended to and made 0600, and on unix one others can read or write is refused with the `chmod 600` that fixes it.
- **It rotates at 20 MiB, keeping four old files.** When it would pass 20 MiB it moves to `<name>.1`. A rotation that cannot move it touches no older file, so the log keeps growing, and waits another 20 MiB before trying again; a `<name>.0` or `<name>.folding` a crash left mid-rotation joins the chain rather than being written over. If the new file cannot be opened, the log goes to stderr until it can, tried again after a minute or another 20 MiB, and each switch is said once. One log file belongs to one server.
- **One sentence for a file only its owner may use.** `server.toml`, `auth.token_file` and the log file are refused in the same words, "readable or writable by other users", which is what the check has always looked at.

### Changed for people coming from 1.3.2

Nothing for an account you already have, except that its home stops sharing an organisation's cached policy and remote settings, as said below, and the login's consent to those settings and the attestation saved with them, as said above. The listing gains `api key` under USAGE for a key account, and JSON gains `"credential":"apikey"` and `"name"` for one; an ordinary account is rendered as it was.

For an account rota holds no access token for, `rota list` warns that it holds no access token, so the usage is not asked, instead of printing a network error, and asks the network nothing about it; one that holds a refresh token is refreshed first instead.

**The `rota` program is a module of its own** from 1.4.0-beta.2: `github.com/professor93/rota/cmd/rota`, which requires `github.com/professor93/rota`, the SDK and the server, at the same version. The root still requires nothing, so a program that imports `rota/lib` or any other of its packages sees no change, and its `go.mod` and `go.sum` never gain what the `rota` program comes to need. Each version is two tags, `vX.Y.Z` and `cmd/rota/vX.Y.Z`. `go install github.com/professor93/rota/cmd/rota@<version>` works as before, for this version and every older one. While 1.4.0 is in beta, `@latest` gives the newest beta, because the program's module has no other versions yet; `install.sh` stays on the last stable release. A checkout builds as it did: `go.work` puts both modules in one workspace. Testing one is `go test work`, since `go test ./...` at the root now leaves the program out. The linux-amd64 binary of 1.4.0-beta.2 is 10.4 MB; later betas give theirs beside it.

**An organisation's cached policy and remote settings are each account's own** from 1.4.0-beta.2. `policy-limits.json`, `remote-settings.json` and every name that is one of them followed by a dot, such as `policy-limits.json.signature.json` or `remote-settings.json.synced-at`, are no longer linked from your Claude directory into an account's home, so one organisation's policy or settings never apply under another account. A link an older rota made for one of them goes on the first launch that finds the home quiet; a real file of that name in the home, and your own files, are left as they are.

### What to do

Nothing, unless you want an account on a key: `rota login --key`, then `rota <id> "..."`. It starts out of the rotation; `rota set <id> --order last` puts it in.

### An account on a key

- The key is checked once, at login, with one request to the API's model list. A `401` or `403` refuses it and nothing is stored; anything else takes it with a warning. It is stored in `accounts.json` with every other credential, mode 0600, and named by a fingerprint of the key, so pasting the same key again is the same account.
- It starts at order 0, out of the rotation, because every run on it costs money. In the queue it counts as unmetered: no usage is ever read for it, and no percentage is shown.
- It runs like any claude account, in its own home, with your settings and the conversations `--sessions` says, its own daemon, and hermetic and headless runs, on `ANTHROPIC_API_KEY` alone. Every other credential variable is dropped, no login is written into its home, and nothing is refreshed.
- It cannot have Remote Control, which Claude Code refuses for API keys: `--remote-control` and `rota set --remote-control on` refuse it by name. It has no usage to read, takes no long-lived token, and has none of the claude.ai features that need a login.
- Claude Code asks once, the first time it opens interactively on the account, whether to use the key. It records the answer in `customApiKeyResponses` in `.claude.json`, keeping the key's last twenty characters there. A key account's `.claude.json` is your own, shared with every account, as 1.3 shares it: an account is isolated by its tokens and its daemon, and nothing more is made private without asking.
- A pasted setup token cannot say whose it is or when it was made, and rota says so in one line when it stores one: a token from another claude.ai account would bill that account.

### For the SDK

- `Paste(ctx, provider, s)` takes a pasted credential and says by its shape which it is, in `Token.Credential`: `"apikey"`, checked once against `ClaudeModelsEndpoint`, with `unverified` beside the token when the API could not be asked, or `"setup-token"`, the token `BeginLong` would have obtained, for `Account.ApplyLong`. Only claude takes either.
- `Account.APIKey()` says an account runs on a key; `Usage` reads nothing for one, and `Stage` launches it on the key alone. `Account.Credential` and `Account.Name` are its new fields, and `Token.Credential` the token's.
- `ClaudeEndpoints` is unchanged: the key check's endpoint is a variable of its own.
- In `rota/store`, `LoginKey` and `PasteLong` keep a pasted key or token, and `PastedLongCaveat` is the line said about a pasted token. In `rota/wire`, `HoldsSecret` and `Unsecret` find and take out anything shaped like an Anthropic credential.
- `Usage` sends nothing for a claude account that holds no access token and answers `ErrReauth`, where it used to ask the usage endpoint without one and pass on the refusal.

### A stopped watcher

- A watcher stopped by an interrupt, SIGTERM or SIGHUP writes "account N: stopped by a signal" to its log before it lets go of its lock, so whoever then finds the lock free can read why.

### After a panic

- A launch or a sweep that panics lets go of the account's claim, and a write that panics leaves no temporary file behind.
- A terminal or an open run whose start panics in the server ends what it started and lets go of the account and its slot.
- A handover that panics or fails before it reaches the CLI lets go of the account's claim, and one that reaches the CLI passes it on as before.

In each case the panic still reaches the caller unchanged.

### Tests

- The test catalog copies its models, as every catalog must, so the catalog tests pass when run more than once.
- The handover test checks its own claim rather than one a deliberately panicking launch test left held, so it passes when run more than once. That leftover claim was a launch that panics inside `prepareShared`, which now lets go of its claim as well, as said under After a panic.
