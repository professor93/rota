## rota 1.3.0

### Changed for people coming from 1.2.0

- **A claude account runs on a login of its own.** A launch in the account's home writes the account's login into Claude Code's own credential store there — `.credentials.json` in the home, which on macOS Claude Code moves into a keychain item named for that home — and puts nothing that authenticates in the environment. Claude Code refreshes the login itself and shares it between every window, the daemon and the background sessions it hosts, so nothing an account runs ends at `OAuth token revoked` any more.
- **Claude Code's own Remote Control works under a rota account.** It was refused for a token handed over in the environment, which is how every launch ran until now. It also acts as whoever the home's `.claude.json` names, so it is a setting: `rota run <id> --remote-control[=name]`, or `rota set <id> --remote-control on` and then `/remote-control` inside a session. See *Remote Control* below.
- **Every account has its own login and its own daemon, and nothing an account's processes authenticate with is ever read by another's.** Besides the login and the daemon's files, these are now each account's own in every mode: `telemetry`, `policy-limits.json`, `statsig`, `mcp-needs-auth-cache.json`, `bridge-spawn`, every `*.lock`, and `backups/` when the account keeps its own configuration file. A link an older rota made for one of them goes on the first launch that finds the home quiet. Background sessions and agent teams are part of the conversations and follow the account's sessions setting, as before.
- **Many runs of one claude account go at once, as before, and rota never writes or refreshes its login while Claude Code runs in its home.** That home owns the login then: rota reads what Claude Code rotated, launches on the login that is there, and leaves the rest for the first moment nothing of Claude Code's is alive.
- **A login rota cannot place is left alone.** When the home holds a login made inside Claude Code that the provider cannot be asked about yet — its access token lapsed overnight, say — a store that cannot be read while something runs there, or no login at all where the account's own was while Claude Code still runs there, rota refreshes nothing for that account, writes nothing and stops nothing, launches on what the home holds, and says so in one line. The next launch or listing that can confirm the login takes it. Nothing to do but launch the account; if it never settles, `rota login` gives it a fresh login.
- **A refused refresh token is never presented again.** The account is dead, and a dead account is refreshed nowhere. When its home holds a login made inside Claude Code that is waiting to be confirmed, it still launches there on that login, and is alive again once that login is confirmed.
- **A directory you chose is treated as possibly yours.** A login there that rota did not write is asked about first; somebody else's is left exactly where it is and the account runs beside it on its own token; moving or removing the account takes a login out of it only when it is provably the account's own.
- **`ROTA_CLAUDE_HOME`** tells everything rota launches which Claude Code directory is yours, so a rota started inside one of its sessions never takes an account's home, or a hermetic run's throwaway directory, for yours.
- **One home, one account.** `rota set --config` and `PATCH config_dir` refuse a directory that is already another account's home — under any spelling, on a volume that ignores case — and two accounts that already share one are not launched there. Changing a claude account's `--config`, or clearing it, reads the home it leaves first, keeps any rotation found there, and then takes its login out of that home — keychain item first; it is refused while Claude Code runs there or the home is in the hold.
- **The long-lived token is for runs without a home.** A launch in the account's home runs on its stored login whether or not a long token is there. `--stateless` and hermetic runs, which take a throwaway directory, still go on a token in their environment — the long one when there is one — and so does an account whose login is dead, when you name it. Such a run on an expired ordinary token, while Claude Code runs in the home, is refused and told that a long-lived token is what it is for.
- **Removing a claude account stops its daemon.** It used to delete the home and leave the daemon running. The daemon is stopped, the home given a few seconds to go quiet, and the removal refused with what is still alive if it does not; on macOS the keychain item goes before the home.
- **`rota login` reads the plan once.** Finishing an ordinary claude login reads the profile with the fresh token, to know the plan and the organisation's name a stored login carries. A profile that cannot be read never fails a login.
- `rota list` says one line about an account's login in its last five days, when Claude Code has recorded when it ends. `--json` and `GET /v1/accounts` carry `login_until`, and `remote_control` when it is on; `PATCH /v1/accounts/{id}` takes `"remote_control": true|false`.

### What to do

Log each claude account in once more with `rota login`, or run `/login` inside one of its windows: either gives the account a login rota can keep in its home. Nothing else is needed.

Windows opened under an earlier rota go on running on the token they were given. While any of them is open, a new launch of that account goes the same way — without Remote Control, refreshing the account's token when it has expired, as before — and rota says so; the first launch after they are closed moves the account onto its stored login, stopping a daemon that was started on the old token and is running alone.

### A login of its own

- One owner per login. While a rota run holds the account, its `daemon.lock` names a live process, or any `sessions/<pid>.json` does — or a record cannot be read — rota reads the home and does not write its store, refresh its login, or rewrite its `.claude.json`. When nothing is alive, a refresh is followed at once, after the store is saved, by writing the new login into the home.
- A rotation by Claude Code keeps the login's `refreshTokenExpiresAt` and is taken with no network call. A login with another one — somebody ran `/login` inside the home — is checked with the provider before anything of it is taken: the same account's is taken, and revives an account marked dead; another account's is refused, the account's own tokens stay as they were, and rota names both.
- A write replaces only the login. Claude Code keeps the OAuth tokens of MCP servers and secrets of its own in the same store, and they stay exactly as they were. On macOS the new file is written and synced first, then the keychain item is removed, then the file is renamed into place, so a removal that fails changes nothing; rota never writes a keychain item. A file left stale beside a keychain item is removed.
- A launch that takes another route than the one the home's daemon was started on stops that daemon — which would otherwise go on serving its old credential to every background session — when nothing but the daemon and the sessions it hosts runs there, and says so. A daemon beside a window somebody has open is left alone, and in a directory you chose with nothing remembered no daemon is stopped.
- A run's claim on the account stays with rota and is never inherited by another program it starts; only the handover, in which rota becomes the CLI, passes it on.
- A rota started inside a session rota launched knows the `CLAUDE_CONFIG_DIR` it inherited is that account's home, not yours.
- A store whose lock a run has released — the reading `--with quota` takes after a run — rotates nothing: no refresh request, nothing written.
- The SDK says how: the claude provider adopts, plans and launches on both routes, `SharedHome`, `StoresLogin`, `HoldsLogin` and `JoinHome` describe and join a home many processes share, `MergeClaudeCredentials` writes a planned login into an existing store, `Account.StagedWritten` records an application's own write, a login somebody made inside the home comes back from adoption as a `*NewLogin` to `Accept` or `Refuse`, and a store that cannot be read is `ErrUnreadableLogin`. `Stage(a, "")` is the environment route, as it always was; on macOS `Stage` and `Adopt` keep to it with any home, and the stored route goes through `StagePlan` and `AdoptFrom`, because the login lives in a keychain item there. A hermetic run of a command staged on the stored route is given the account's token on the way.

### Remote Control

- By default an account shares your whole Claude Code configuration — settings, memory, skills, plugins, the `.claude.json` with its MCP servers and trusted folders, and so the identity record in it. The login itself is always the account's own.
- With the setting on, the account keeps its own `.claude.json`: a copy of yours without your identity, given the account's, and from then on its own. Every launch folds in, one way and only by adding, the top-level settings, projects and MCP servers yours has and it lacks, and a folder you have trusted since. MCP servers and trusted folders added inside the account are seen only there.
- Turning it off puts the copy aside as `.claude.json.own`, never deleting it, and links yours again; turning it on again brings the same copy back. Either switch waits for a launch that finds the home quiet, and rota says so meanwhile.
- MCP servers that sign in with OAuth are authorized per account home in both modes: those tokens live in each home's credential store.
- One caveat is Claude Code's own: a login in another configuration directory on the same machine can interrupt one account's Remote Control.

### What stays the same

- Your own login — your Claude Code directory (`~/.claude`, or the `CLAUDE_CONFIG_DIR` rota was started with when nothing launched it) and its keychain item — is never read or written. A home rota made is rota's to write and read, that home's keychain item on macOS included; in a directory you chose, rota replaces or removes a login only when it is provably the account's. An account told that its configuration directory is yours stays on a token in the environment.
- Windows keeps the environment route for claude in every case.
- On macOS a home whose path is not plain ASCII cannot keep a login: the keychain item's name cannot be worked out without Unicode normalisation, which the standard library does not have, so rota could not follow it. Such an account runs on a token, without Remote Control, and rota says so once per launch.
